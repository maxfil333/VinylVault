# Деплой VinylVault на сервер

Пошаговая инструкция для развёртывания с нуля на чистом сервере с Ubuntu. Каждая команда разобрана по аргументам:
что она делает, зачем нужна и что будет, если её пропустить.

Все команды выполняются на сервере по SSH, если в тексте прямо не сказано «на своей машине».

---

## 1. Зачем нужен nginx

Приложение умеет только одно: слушать обычный HTTP на порту 8000. Оно не знает, что такое TLS-сертификаты,
не умеет отвечать на 443-м порту и не понимает, как показать сайт по адресу `https://вашдомен.ру`.

nginx ставится перед приложением и берёт на себя всё остальное. Он слушает публичные порты 80 и 443, держит
сертификат (то есть даёт HTTPS и замочек в браузере), а сам запрос пересылает внутрь машины на `127.0.0.1:8000` —
то есть контейнеру приложения. Такая схема называется **реверс-прокси**: снаружи все видят nginx, а приложение
спрятано и доступно только с самого сервера.

Именно поэтому в `docker-compose.yml` порт публикуется как `127.0.0.1:8000:8000`. Из интернета до приложения
напрямую не дотянуться — единственная дверь ведёт через nginx с шифрованием.

У этой схемы есть важный побочный эффект. Когда nginx пересылает запрос, приложение видит соединение как обычный
незашифрованный HTTP с адреса `127.0.0.1`, потому что для приложения клиент — это nginx, а не браузер. Настоящие
данные о посетителе nginx передаёт отдельными заголовками:

- `X-Forwarded-Proto` — по какой схеме пришёл браузер (`https`). Без него приложение считает соединение
  небезопасным и не ставит флаг `Secure` на cookie сессии, из-за чего cookie может уйти по открытому HTTP.
- `X-Forwarded-For` — реальный IP посетителя. Без reverse proxy твой FastAPI может видеть IP самого Nginx: 
`request.client.host = 127.0.0.1`,
а через X-Forwarded-For можно узнать реальный IP пользователя.

Приложение верит этим заголовкам только от доверенного прокси — за это отвечает переменная `FORWARDED_ALLOW_IPS`
в `.env`. В конфиге nginx за это отвечают строки `proxy_set_header`. Обе части обязательны, иначе получится
HTTPS-сайт с незащищённой сессионной cookie.

## 2. Что нужно подготовить

**Сервер.** VPS с Ubuntu 22.04 или 24.04, минимум 2 ГБ оперативной памяти (MongoDB + приложение + nginx).
Доступ по SSH, права root или пользователь с `sudo`.

**Домен.** В панели регистратора создайте A-запись, указывающую на IP сервера: имя `@` (для `example.com`) или
`vinylvault` (для `vinylvault.example.com`), значение — IP-адрес сервера. 
```
A * -> 130.17.0.0
A @ -> 130.17.0.0
A www -> 130.17.0.0
```
Проверить, что запись разошлась:

```bash
ping -c 2 example.com
```

- `-c 2` — отправить всего 2 пакета и выйти (иначе `ping` работает бесконечно).

В ответе должен быть IP вашего сервера. Если видите старый адрес или ошибку — сертификат позже выпустить не
получится, нужно дождаться обновления DNS (обычно минуты, иногда до часа).

**Ключи.** Пароли и ключи из локального `.env`: `API_KEY` (Last.fm) и группа `s3_*` (Selectel). Пароли для Mongo
на сервере нужно сгенерировать новые, локальные для прода не годятся.

## 3. Обновить систему

```bash
sudo apt update && sudo apt upgrade -y
```

- `apt update` — обновляет список доступных пакетов из репозиториев. Сами программы при этом не меняются.
- `&&` — выполнить вторую команду только если первая завершилась успешно.
- `apt upgrade` — обновляет уже установленные пакеты до актуальных версий.
- `-y` — автоматически отвечать «да» на вопросы, чтобы установка не останавливалась в ожидании ввода.

Зачем: свежие обновления безопасности на машине, которая будет доступна из интернета.

## 4. Установить Docker

```bash
curl -fsSL https://get.docker.com | sudo sh
```

- `curl` — скачивает файл по URL. Здесь скачивается официальный скрипт установки Docker.
- `-f` (`--fail`) — при ошибке сервера (например, 404) не выводить страницу ошибки как «полезные данные»,
  а вернуть код ошибки. Без этого можно случайно выполнить HTML-страницу как скрипт.
- `-s` (`--silent`) — не показывать индикатор прогресса.
- `-S` (`--show-error`) — но ошибки всё-таки показывать (`-s` сам по себе их тоже скрывает).
- `-L` (`--location`) — следовать за редиректами, иначе получите пустой ответ вместо скрипта.
- `| sudo sh` — передать скачанный скрипт на выполнение оболочке `sh` с правами root.

Проверить, что всё встало:

```bash
sudo docker --version
sudo docker compose version
```

Docker Compose здесь встроен в сам Docker (подкоманда `docker compose`, без дефиса), отдельно ставить не нужно.

Опционально можно избавиться от `sudo` перед каждым `docker`:

```bash
sudo usermod -aG docker $USER
```

- `usermod` — изменяет параметры пользователя.
- `-aG docker` — добавить (`-a`, append) пользователя в группу (`-G`) `docker`. Без `-a` пользователь будет удалён
  из всех остальных групп, это частая и болезненная ошибка.
- `$USER` — переменная окружения с именем текущего пользователя.

После этого нужно выйти из SSH и зайти заново, чтобы новая группа применилась. В инструкции ниже `sudo` оставлен
везде — так команды работают в любом случае.

## 5. Установить nginx, certbot и git

```bash
sudo apt install -y nginx certbot python3-certbot-nginx git
```

- `nginx` — сам веб-сервер и реверс-прокси.
- `certbot` — утилита для получения бесплатных TLS-сертификатов Let's Encrypt.
- `python3-certbot-nginx` — плагин, благодаря которому certbot умеет сам править конфиги nginx и перезагружать его.
- `git` — чтобы забрать код проекта и потом обновлять его одной командой.

После установки nginx уже запущен и отдаёт стандартную страницу-заглушку. Проверить:

```bash
sudo systemctl status nginx
```

- `systemctl` — управление системными службами.
- `status nginx` — показать состояние службы. Ожидаемое: `active (running)`. Выйти из просмотра — `q`.

## 6. Настроить файрвол

```bash
sudo ufw allow OpenSSH
sudo ufw allow 'Nginx Full'
sudo ufw enable
sudo ufw status
```

- `ufw` — простой интерфейс к системному файрволу.
- `allow OpenSSH` — разрешить входящие соединения на порт 22. **Делать это нужно до `enable`**, иначе вы
  заблокируете сами себя и потеряете доступ к серверу.
- `allow 'Nginx Full'` — готовый профиль, открывающий сразу порты 80 (HTTP) и 443 (HTTPS). Кавычки нужны из-за
  пробела в названии.
- `enable` — включить файрвол (спросит подтверждение, ответьте `y`).
- `status` — показать список правил.

Порт 8000 не открываем никогда: приложение слушает только localhost и должно быть доступно исключительно nginx.
Порт 27017 (MongoDB) тоже не открываем — база вообще не публикует портов на хост.

## 8. Заполнить `.env`

Файл `.env` в git не хранится (в нём секреты), поэтому его нужно создать на сервере.

```bash
sudo cp .env.example .env
sudo nano .env
```

- `cp .env.example .env` — скопировать шаблон в рабочий файл.
- `nano` — простой текстовый редактор. Сохранить: `Ctrl+O`, затем `Enter`. Выйти: `Ctrl+X`.

Сначала сгенерируйте пароли для базы:

```bash
openssl rand -base64 24
```

- `openssl rand` — генератор случайных байт.
- `-base64` — вывести результат в виде печатаемой строки.
- `24` — количество случайных байт (получится строка около 32 символов).

Запустите команду несколько раз и используйте разные результаты для разных паролей.

Что должно оказаться в `.env` на проде:

```bash
# Last.fm и Selectel S3 — переносим из локального .env
API_KEY=...
s3_user=...
s3_password=...
s3_access_key=...
s3_secret_key=...
s3_endpoint=https://s3.ru-3.storage.selcloud.ru
s3_base_domain=https://<ваш-id>.selstorage.ru

# Пароли базы — новые, сгенерированные, не те же, что локально
MONGO_ROOT_USER=vinyl
MONGO_ROOT_PASSWORD=<сгенерированный пароль>
MONGO_URI=mongodb://vinyl:<тот же пароль>@127.0.0.1:27017/?authSource=admin&directConnection=true

# Настройки прода
COOKIE_SECURE=true
FORWARDED_ALLOW_IPS=*
ENABLE_DOCS=false
APP_BIND_HOST=127.0.0.1
LOG_LEVEL=INFO
```

Почему именно так:

- `COOKIE_SECURE=true` — cookie сессии уходит только по HTTPS. На проде обязательно; локально по `http://localhost`
  наоборот должно быть `false`, иначе браузер откажется её сохранять.
- `FORWARDED_ALLOW_IPS=*` — верить заголовкам `X-Forwarded-*`. Звёздочка здесь безопасна ровно потому, что
  `APP_BIND_HOST=127.0.0.1`: до приложения дотягивается только nginx с этой же машины, подделать заголовки
  снаружи невозможно.
- `ENABLE_DOCS=false` — не публиковать `/docs`, `/redoc` и `/openapi.json`.
- `APP_BIND_HOST=127.0.0.1` — порт 8000 виден только внутри сервера.
- `MONGO_URI` в `.env` нужен для запуска приложения без docker и для вспомогательных скриптов. Внутри compose
  приложение получает свой адрес (`@mongo:27017`) из `docker-compose.yml`, эта строка его не переопределяет.

Важно про пароль Mongo: он применяется **только при первом создании базы**, когда том `mongo_data` ещё пустой.
Если поменять пароль позже, база продолжит жить со старым, и приложение перестанет подключаться. Поэтому пароли
нужно решить сразу, до первого запуска.

Альтернатива ручному заполнению — скопировать готовый файл со своей машины. Команда выполняется **в локальном
PowerShell**, не на сервере:

```powershell
scp .env root@ВАШ_IP:/srv/VinylVault/.env
```

- `scp` — копирование файлов по SSH.
- `.env` — что копируем (файл в текущем каталоге проекта).
- `root@ВАШ_IP:/srv/VinylVault/.env` — куда: пользователь, адрес сервера и полный путь назначения.

Не забудьте после копирования поправить в нём прод-значения (`COOKIE_SECURE`, пароли и остальное).

## 9. Запустить приложение

```bash
sudo docker compose up -d --build
```

- `docker compose up` — поднять все сервисы из `docker-compose.yml` (приложение и MongoDB).
- `-d` (`--detach`) — запустить в фоне и вернуть управление терминалу. Без этого логи будут литься в консоль,
  а `Ctrl+C` остановит сервисы.
- `--build` — сначала собрать образ приложения из `Dockerfile`. Нужно при первом запуске и после каждого
  изменения кода.

Первая сборка занимает несколько минут: скачиваются базовые образы Python и MongoDB, устанавливаются зависимости.

Проверить состояние:

```bash
sudo docker compose ps
```

Ожидаемый результат — две строки со статусом `Up ... (healthy)`:

```
NAME                 SERVICE   STATUS
vinylvault-app-1     app       Up 30 seconds (healthy)
vinylvault-mongo-1   mongo     Up 40 seconds (healthy)
```

Слово `healthy` означает, что встроенная проба сходила на `/health` и приложение ответило, что база на связи.
Если статус `starting` — подождите 20–30 секунд. Если `unhealthy` — смотрите логи (раздел 13).

Проверить приложение напрямую, изнутри сервера:

```bash
curl -s http://127.0.0.1:8000/health
```

- `-s` — без индикатора прогресса, чтобы вывод был чистым.

Ожидаемый ответ: `{"status":"ok","database":"up"}`. Из браузера сайт пока не откроется — это нормально, nginx
ещё не настроен.

## 10. Настроить nginx по HTTP

Сначала делаем конфиг без шифрования: certbot должен иметь возможность подтвердить владение доменом по HTTP,
а сертификата на сервере пока нет.

```bash
sudo nano /etc/nginx/sites-available/vinylvault
```

Каталог `sites-available` — это «все написанные конфиги», а `sites-enabled` — «включённые». Вставьте текст,
заменив `example.com` на свой домен:

```nginx
server {
    listen 80;
    server_name example.com;

    client_max_body_size 6m;

    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Разбор конфига:

- `server { ... }` — описание одного виртуального сайта.
- `listen 80` — принимать обычные HTTP-соединения.
- `server_name example.com` — для какого домена этот блок. По нему nginx выбирает конфиг, если на сервере
  несколько сайтов.
- `client_max_body_size 6m` — максимальный размер загружаемого файла. По умолчанию nginx рубит запросы больше 1 МБ
  и отдаёт ошибку 413 ещё до приложения, из-за чего сломалась бы загрузка аватаров (лимит приложения — 5 МБ,
  плюс запас на служебные данные формы).
- `location / { ... }` — правила для всех путей сайта.
- `proxy_pass http://127.0.0.1:8000` — куда пересылать запрос: контейнеру приложения на локальный порт.
- `proxy_http_version 1.1` — общаться с приложением по HTTP/1.1 (по умолчанию nginx использует 1.0, что мешает
  keep-alive соединениям).
- `proxy_set_header Host $host` — передать приложению исходное имя домена, иначе оно увидит `127.0.0.1` и может
  построить неверные ссылки в редиректах.
- `proxy_set_header X-Real-IP $remote_addr` — IP посетителя в отдельном заголовке (для логов).
- `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` — цепочка IP-адресов клиента. По ней приложение
  считает лимиты запросов на пользователя.
- `proxy_set_header X-Forwarded-Proto $scheme` — схема запроса (`http` или `https`). Ключевая строка: без неё
  сессионная cookie не получит флаг `Secure`.

Включаем конфиг:

```bash
sudo ln -s /etc/nginx/sites-available/vinylvault /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx
```

- `ln -s <источник> <куда>` — создать символическую ссылку (`-s`), то есть «ярлык». Так конфиг из
  `sites-available` становится включённым, оставаясь единственным файлом.
- `rm -f .../default` — удалить ссылку на стандартный сайт-заглушку nginx, иначе он может перехватывать запросы.
  `-f` не ругается, если файла уже нет.
- `nginx -t` — проверить синтаксис всех конфигов, ничего не применяя. Ожидаемый вывод: `syntax is ok` и
  `test is successful`. Всегда запускайте это перед перезагрузкой.
- `systemctl reload nginx` — перечитать конфиги без разрыва текущих соединений (в отличие от `restart`,
  который останавливает и запускает сервер заново).

Теперь сайт должен открываться в браузере по `http://example.com`.

## 11. Включить HTTPS

```bash
sudo certbot --nginx -d example.com
```

- `--nginx` — использовать плагин для nginx: certbot сам подтвердит домен, положит сертификат и **перепишет ваш
  конфиг**, добавив блок `listen 443 ssl`, пути к сертификатам и редирект с HTTP на HTTPS.
- `-d example.com` — домен, для которого выпускается сертификат. Если сайт должен работать и с `www`, укажите
  оба: `-d example.com -d www.example.com`.

Certbot спросит email (для писем об истечении сертификата) и согласие с условиями. По окончании он сам
перезагрузит nginx.

Важно: ваши строки `proxy_set_header` при этом сохраняются — certbot добавляет свои директивы, не удаляя
существующий `location`. Убедиться можно так:

```bash
sudo grep -n 'X-Forwarded-Proto\|listen 443' /etc/nginx/sites-available/vinylvault
```

- `grep` — поиск строк по шаблону.
- `-n` — показывать номера строк.
- `\|` — «или» в шаблоне: ищем сразу две подстроки.

Должны найтись обе: и `listen 443 ssl`, и `proxy_set_header X-Forwarded-Proto $scheme`.

Сертификаты Let's Encrypt живут 90 дней и продлеваются автоматически системным таймером. Проверить, что
продление рабочее:

```bash
sudo certbot renew --dry-run
sudo systemctl list-timers | grep certbot
```

- `renew` — продлить все сертификаты, которым это нужно.
- `--dry-run` — «холостой прогон»: проверить весь процесс, ничего не меняя. Полезно, потому что у Let's Encrypt
  есть лимиты на количество реальных выпусков.
- `list-timers` — список запланированных системных таймеров; `grep certbot` оставляет только нужную строку.
  В выводе видно, когда состоится следующая попытка продления.

Файл `deploy/nginx.conf.example` в репозитории — это пример готового конфига с TLS, для сверки после работы
certbot или для ручной настройки. Копировать его до выпуска сертификата нельзя: он ссылается на файлы в
`/etc/letsencrypt`, которых ещё нет, и `nginx -t` выдаст ошибку.

## 12. Проверить, что всё работает

```bash
curl -s https://example.com/health
```

Ожидаемо: `{"status":"ok","database":"up"}`. Это подтверждает всю цепочку: TLS, nginx, приложение, база.

```bash
curl -sI http://example.com
```

- `-I` (`--head`) — запросить только заголовки ответа, без тела страницы.

Ожидаемо: `HTTP/1.1 301 Moved Permanently` и `Location: https://example.com/` — то есть редирект с HTTP на HTTPS,
который добавил certbot.

Проверка флага `Secure` у сессионной cookie — самая важная, ради неё и нужны заголовки прокси. Зарегистрируйтесь
на сайте через браузер, затем откройте инструменты разработчика (F12) → Application (или Storage) → Cookies и
убедитесь, что у cookie `vv_session_cookie` стоят галочки `HttpOnly` и `Secure`.

Дальше пройдите обычный пользовательский путь: регистрация, поиск альбома, добавление в коллекцию, смена аватара,
перетаскивание карточек и `Save`. Это проверяет Last.fm, S3 и запись в базу.

Скрипт `scripts/docker_smoke_test.py` рассчитан на локальный стек и требует Python с `httpx`, на сервере его
запускать не обязательно.

## 13. Логи

```bash
sudo docker compose logs -f app
```

- `logs` — вывести логи контейнера.
- `-f` (`--follow`) — продолжать показывать новые строки в реальном времени. Выйти — `Ctrl+C`.
- `app` — имя сервиса. Без него покажутся логи всех сервисов сразу.

Полезные варианты:

```bash
sudo docker compose logs --tail 50 app
sudo docker compose logs --since 10m app
```

- `--tail 50` — только последние 50 строк.
- `--since 10m` — только за последние 10 минут.

Файловые логи приложения лежат в отдельном docker-томе с ротацией и удалением архивов старше 14 дней:

```bash
sudo docker compose exec app ls -la /app/__logs
```

- `exec <сервис> <команда>` — выполнить команду внутри работающего контейнера.
- `ls -la` — подробный список файлов, включая скрытые.

Логи nginx лежат на самом сервере:

```bash
sudo tail -f /var/log/nginx/access.log
sudo tail -n 50 /var/log/nginx/error.log
```

- `tail` — показать конец файла.
- `-f` — следить за новыми строками.
- `-n 50` — показать последние 50 строк.

## 14. Обновление после изменений в коде

На своей машине закоммитили и отправили изменения в GitHub, затем на сервере:

```bash
cd /srv/VinylVault
sudo git pull
sudo docker compose up -d --build
sudo docker compose ps
```

- `git pull` — забрать новые коммиты из репозитория.
- `up -d --build` — пересобрать образ и перезапустить только те контейнеры, которых коснулись изменения.
  База при этом не трогается, данные сохраняются.
- `ps` — дождаться, пока `app` снова станет `healthy`.

Если менялся только `.env` (без изменений кода), пересборка не нужна:

```bash
sudo docker compose up -d
```

Compose увидит новые переменные окружения и пересоздаст контейнер приложения.

Остановить всё:

```bash
sudo docker compose down
```

- `down` — остановить и удалить контейнеры. Данные в томах (`mongo_data`, `app_logs`) остаются.

Флаг `-v` у `down` **удаляет тома вместе с базой данных**. Использовать его на проде нельзя.

## 15. Бэкапы базы

В проекте есть готовый скрипт `scripts/mongo_backup.sh`: он делает сжатый дамп базы в каталог `./backups`
и удаляет архивы старше 14 дней.

Первый запуск руками, чтобы убедиться, что всё работает:

```bash
cd /srv/VinylVault
sudo chmod +x scripts/mongo_backup.sh
sudo ./scripts/mongo_backup.sh
```

- `chmod +x <файл>` — выдать файлу право на выполнение. Делается один раз; без этого ни вы, ни cron скрипт
  не запустите.
- `./scripts/mongo_backup.sh` — запуск скрипта. `./` означает «из текущего каталога» и обязателен: без него
  оболочка ищет команду только в системных путях.

Успешный вывод выглядит так: `OK: ./backups/vinylvault-20260821-030000.archive.gz (12K)`.

Если появилась ошибка `/usr/bin/env: 'bash\r': No such file or directory`, значит файл попал на сервер с
виндовыми переводами строк. Лечится так:

```bash
sudo sed -i 's/\r$//' scripts/mongo_backup.sh
```

- `sed` — потоковый редактор текста.
- `-i` — править файл на месте.
- `'s/\r$//'` — заменить символ возврата каретки в конце каждой строки на пустоту.

### Расписание через cron

`cron` — встроенный планировщик: он сам запускает команды по расписанию, пока сервер работает. Расписание
хранится в текстовом файле, где каждая строка — одно задание.

```bash
sudo crontab -e
```

- `crontab` — работа с файлом расписаний.
- `-e` (`--edit`) — открыть его в редакторе. При первом запуске система спросит редактор, выбирайте `nano`
  (обычно вариант `1`).

Спуститесь в самый низ файла (строки, начинающиеся с `#`, — это комментарии, их не трогаем) и допишите одну
строку:

```
30 3 * * * cd /srv/VinylVault && ./scripts/mongo_backup.sh >> /var/log/vv-backup.log 2>&1
```

Сохранить: `Ctrl+O`, `Enter`, затем `Ctrl+X`. В терминале появится `crontab: installing new crontab`.

Разбор строки:

- `30 3 * * *` — расписание из пяти полей: минута, час, день месяца, месяц, день недели. Читается как
  «в 3:30 каждый день». Звёздочка означает «любое значение».
- `cd /srv/VinylVault` — обязательно: cron запускает команды из домашнего каталога, а скрипту нужны `.env` и
  `docker-compose.yml` из каталога проекта.
- `&& ./scripts/mongo_backup.sh` — сам бэкап, выполнится только если `cd` удался.
- `>> /var/log/vv-backup.log` — дописывать вывод в конец файла журнала (одна `>` перезаписывала бы его каждый раз).
- `2>&1` — направить туда же поток ошибок (`2`), а не только обычный вывод (`1`). Иначе ошибки бэкапа
  никуда не попадут и вы о них не узнаете.

Проверить, что задание записалось, и посмотреть результаты ночных запусков:

```bash
sudo crontab -l
sudo tail -n 20 /var/log/vv-backup.log
```

- `-l` (`--list`) — напечатать текущее расписание.

### Восстановление из дампа

```bash
sudo docker compose exec -T mongo mongorestore \
  --username vinyl --password 'ВАШ_ПАРОЛЬ' --authenticationDatabase admin \
  --archive --gzip --drop < backups/vinylvault-20260821-030000.archive.gz
```

- `exec -T` — выполнить команду в контейнере без выделения терминала. Обязательно, когда данные подаются
  на вход через `<`.
- `mongorestore` — штатная утилита восстановления MongoDB.
- `--username`, `--password`, `--authenticationDatabase admin` — данные для входа в базу (те же, что в `.env`).
- `--archive` — читать данные из потока-архива, а не из каталога с файлами.
- `--gzip` — архив сжат.
- `--drop` — перед восстановлением удалить существующие коллекции, чтобы не смешать старые и новые записи.
- `< backups/...gz` — подать файл дампа на стандартный вход команды.

## 16. Посмотреть данные в базе

Порт MongoDB наружу не опубликован, поэтому подключаться нужно изнутри сервера.

```bash
cd /srv/VinylVault
sudo docker compose exec -it mongo mongosh -u vinyl -p --authenticationDatabase admin VinylVault
```

- `exec -it mongo` — запустить команду внутри контейнера базы в интерактивном режиме (`-i` — держать вход
  открытым, `-t` — выделить терминал).
- `mongosh` — консольный клиент MongoDB.
- `-u vinyl` — имя пользователя из `MONGO_ROOT_USER`.
- `-p` без значения — спросить пароль отдельно, чтобы он не остался в истории команд.
- `--authenticationDatabase admin` — где хранится учётная запись (root-пользователь Mongo живёт в базе `admin`).
- `VinylVault` — база, в которую сразу попадаем.

Внутри оболочки запросы пишутся на JavaScript:

```javascript
show collections                                  // список коллекций
db.users_collection.countDocuments()              // сколько всего пользователей
db.users_collection.distinct("username")          // список имён массивом
db.users_collection.findOne({username: "maxfil333"}, {password: 0})   // один пользователь целиком
db.session_cookies_collection.find({}, {username: 1, login_time: 1, _id: 0}).sort({login_time: -1}).limit(10)
```

Второй аргумент у `find`/`findOne` — проекция, то есть какие поля показать: `1` включает поле, `0` исключает,
`_id: 0` убирает служебный идентификатор. Поле `password` смотреть незачем — там bcrypt-хэш, а не пароль.

Выйти из оболочки: `exit` или `Ctrl+D`.

Тот же список пользователей одной командой, без входа в оболочку:

```bash
sudo docker compose exec mongo mongosh -u vinyl -p --authenticationDatabase admin --quiet \
  --eval 'db.getSiblingDB("VinylVault").users_collection.find({}, {username:1, _id:0}).sort({username:1}).forEach(u => print(u.username))'
```

- `--quiet` — не печатать приветствие и версию, только результат.
- `--eval '<код>'` — выполнить переданный код и выйти.
- `getSiblingDB("VinylVault")` — переключиться на нужную базу (при `--eval` мы стартуем не в ней).
- `forEach(u => print(u.username))` — напечатать по одному имени на строку.

Читающие запросы (`find`, `countDocuments`, `aggregate`, `distinct`) безопасны. А `deleteMany`, `updateMany` и
особенно `drop()` срабатывают мгновенно и без подтверждения — перед любым изменением данных делайте бэкап.

### Веб-админка mongo-express

В проекте есть графическая админка, выключенная по умолчанию и доступная только с localhost. Поднять её
на время:

```bash
sudo docker compose --profile dev up -d mongo-express
```

- `--profile dev` — включить сервисы, помеченные профилем `dev`. Без этого флага mongo-express не запускается,
  поэтому на проде он не работает случайно.

Затем на **своей машине** (в локальном PowerShell) откройте SSH-туннель:

```powershell
ssh -L 8081:127.0.0.1:8081 root@ВАШ_IP
```

- `-L 8081:127.0.0.1:8081` — переадресация локального порта: обращения к `localhost:8081` на вашем компьютере
  уходят по SSH на сервер и там попадают на `127.0.0.1:8081`. Так вы получаете доступ к сервису, который наружу
  не опубликован.

Пока это окно SSH открыто, админка доступна по адресу `http://localhost:8081/mongo`, логин и пароль — из
`MONGO_EXPRESS_USER` и `MONGO_EXPRESS_PASSWORD`. Посмотрели — выключайте:

```bash
sudo docker compose stop mongo-express
```

## 17. Если что-то не работает

**502 Bad Gateway.** nginx работает, а приложение нет. Проверьте `sudo docker compose ps` (статус должен быть
`healthy`) и `sudo docker compose logs --tail 50 app`. Частая причина — неверные ключи в `.env` или
недоступная база.

**413 Request Entity Too Large** при загрузке аватара. В конфиге nginx нет `client_max_body_size 6m`.
Добавьте, затем `sudo nginx -t && sudo systemctl reload nginx`.

**Cookie без флага `Secure`.** Либо в конфиге nginx отсутствует `proxy_set_header X-Forwarded-Proto $scheme`,
либо в `.env` не выставлены `COOKIE_SECURE=true` и `FORWARDED_ALLOW_IPS=*`. После правки `.env` нужен
`sudo docker compose up -d`.

**Все пользователи получают `429 Too Many Requests`.** Приложение не видит реальные IP: проверьте
`X-Forwarded-For` в конфиге nginx и `FORWARDED_ALLOW_IPS` в `.env`.

**Certbot не может подтвердить домен.** A-запись ещё не разошлась (проверьте `ping -c 2 example.com`), закрыт
порт 80 (`sudo ufw status`) или в `server_name` указан другой домен.

**Приложение `unhealthy`, в логах ошибки аутентификации Mongo.** Скорее всего пароль в `.env` поменяли после
первого запуска базы. Пароль root задаётся только при создании тома. Либо верните старый пароль, либо (если
данными можно пожертвовать) удалите том: `sudo docker compose down -v` — это **необратимо стирает базу**.

**Нужно посмотреть, что реально видит приложение.** Заголовки запроса и IP клиента видны в логах:
`sudo docker compose logs --tail 100 app` — там для каждого запроса печатается адрес, который приложение
считает адресом клиента.
